## 1. 목적

`요구사항_정의서.md`에 정의된 5개 앱(account, home, chatbot, records, board)의 기능적/비기능적 요구사항이 실제 화면 동작 기준으로 충족되는지 Playwright 기반 E2E 테스트로 검증한다. 현재 각 앱의 `tests.py`는 빈 스텁 상태이므로, 본 계획서가 사실상 이 프로젝트의 **최초 자동화 테스트 설계**가 된다.

본 문서는 **계획서**만을 산출물로 한다. 테스트 코드 작성·실행·결과보고서 작성은 별도 요청 시 후속 단계로 진행한다.

## 5. 테스트 전략 공통 사항

- **인증**: `board`, `records`, `account`(로그인/회원가입 제외), `chatbot:chat` 페이지는 전부 `login_required`. 대부분의 테스트가 로그인된 상태를 전제로 하므로, 로그인된 `page`를 만들어주는 공용 fixture(예: `authenticated_page`)를 설계 단계에서 최우선으로 만든다.
- **SSE 처리**: `chatbot`의 스트리밍 엔드포인트(`chat-stream`, `chat-stream-new`)는 `text/event-stream` 응답이다. Playwright의 표준 `page.click()` + DOM 폴링(`expect(locator).to_contain_text(...)`, 타임아웃 확장)으로 최종 렌더링 결과를 검증하는 방식을 기본으로 하고, 필요 시 `page.request`로 원본 SSE 프레이밍(`data: {...}\n\n`)을 직접 파싱하는 보조 테스트를 추가한다.
- **실 API 사용에 따른 검증 완화**: 챗봇 응답 "내용"은 결정적이지 않으므로, 답변 텍스트의 정확한 일치가 아니라 (a) 로딩 상태 해제, (b) 최종 답변이 비어있지 않음, (c) 에러 없이 `done` 이벤트 도달 등 **형식/흐름 위주**로 검증한다.
- **JSON/Ajax 엔드포인트**: `board`의 create/update/delete/like/report는 JSON 기반이므로, UI 클릭 후 DOM 변화(모달 닫힘, 카운트 증가 등)와 함께 필요 시 `page.wait_for_response()`로 실제 API 응답 상태코드도 함께 검증한다.

## 8. 환경 구축 제안 (2차 일정에서 착수)

현재 리포지토리에는 pytest/playwright 설정이 전혀 없으므로, 코드 작성에 앞서 아래 골격을 먼저 구축한다.

```
military_life/
├── pytest.ini                 # DJANGO_SETTINGS_MODULE, testpaths 등
├── e2e/
│   ├── conftest.py             # live_server, test_user(+Profile), authenticated_page 등 공용 fixture
│   ├── test_account.py         # TC-ACCT-*
│   ├── test_home.py            # TC-HOME-*
│   ├── test_chatbot.py         # TC-CHAT-*
│   ├── test_records.py         # TC-REC-*
│   └── test_board.py           # TC-BOARD-*
└── ...
```

- `authenticated_page` fixture: 매 테스트마다 UI로 로그인시키면 느려지므로, `live_server` DB에 세션을 미리 만들어 쿠키를 주입하는 방식을 우선 검토
- 챗봇 실 API 테스트는 `OPENAI_API_KEY` 등이 없으면 `pytest.mark.skipif`로 건너뛰도록 하여, 키가 없는 환경(CI 등)에서도 나머지 스위트는 돌아가게 한다

## 9. 완료 기준 (Exit Criteria)

- [구현확인필요] 태그가 붙은 TC(G-1~G-6 관련)는 개발팀 확인 후 "확정" 또는 "요구사항 문서 수정 필요"로 결론이 남
- 그 외 전체 TC가 PASS
- 테스트 실행 후 실 데이터베이스(`military_life/db.sqlite3`)에 변경 없음
- 챗봇 실 API 호출로 발생하는 비용/사용량이 팀 내 공유됨

## 10. 리스크 및 제약사항

- **실 API 사용**: 챗봇 테스트가 실제 OpenAI/Qdrant/neo4j를 호출하므로 (a) 비용 발생, (b) 응답 지연·비결정성으로 인한 테스트 flake 가능성, (c) 외부 서비스 장애 시 무관한 테스트까지 실패할 수 있음. 답변 "내용"이 아닌 "형식/흐름" 위주로 assertion을 설계해 완화하되, 완전히 제거되지는 않음.
- **구현 갭(2절 G-1~G-6)**: 요구사항 문서상 "완료/수용"이지만 화면 기준 미확인/미구현으로 추정되는 항목이 6개 존재. 해당 TC는 실행 전 재확인이 필요하며, 실제로 미구현이라면 이번 테스트에서 의도적으로 "실패"를 재현해 갭을 드러내는 것 자체가 목적이 될 수 있음.
- **최초 자동화 테스트**: 5개 앱의 `tests.py`가 전부 빈 스텁이라 기존 회귀 안전망이 없는 상태에서 시작함. 초기 실행 시 예상보다 많은 실패가 나올 수 있음을 감안해야 함.
- **`.env` 위치 이슈**: 이전 로그인 테스트 계획서에서 확인된 것처럼, `.env`가 `military_life/.env`가 아닌 프로젝트 루트에 있으면 챗봇 관련 키 값이 로드되지 않음. 챗봇 테스트 착수 전 재확인 필요.
- **pytest/playwright 설정 부재**: 8절의 골격 구축이 선행되어야 실제 코드 작성이 가능 — 일정에 별도 반영.
